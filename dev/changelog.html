Changelog#

[Unreleased]#

Changed#

  • MCP server: shorter descriptions, workflows and a banner that names the writer (phase 6-quater, PR 12). The descriptions of the four parameters that every recipe tool has (session_id, provide_missing, max_listed, reason) are 34% shorter, which saves the agent about 11 thousand characters of context over the 65 tools (one text for all the tools, kept in astrocook/mcp_server/schemas.py); what they say about defaults and limits is unchanged. The instructions of the server have a paragraph of typical workflows for the manual fits of Absorbers: which tools fit (absorbers_add_component, absorbers_add_linked_system, absorbers_fit_component) and which only change values and links and need a fit after (absorbers_update_component, absorbers_update_constraint), with examples (adapt a system, try a component, link ions). The banner of a session followed by the GUI says the pid and the version of Astrocook of the program that writes it (e.g. a server of an older version left running); a marker of an earlier version, without them, is still read and its banner is as before. No number or behaviour of the recipes changes.

  • The labels of the menus come from the registry, and the Help button opens the documentation (phase 6-quater, PR 11, F107 and F125). Each recipe in a menu has a key menu in the registry ("Edit > Set &Properties"), the only place where its label is written: the menus are built from it, the dialog is titled by it and the text of the methods names the recipe by it. The labels of the menus are the same; what changes is that Absorbers > Auto-detect Doublets… opens Recipe: Auto-detect Doublets (it was Auto-fit metal doublets (Red Side); the same for the other entries: Set Properties, Smooth Spectrum, …), and that the text of the methods (File > Export Log as Text…) writes the entry as the menu does (Continuum > Auto-estimate Continuum, File > Import Systems from Session), and names no menu for a recipe that has no entry (Convert X axis, Add component, …; it named Edit > Convert X axis, which does not exist). The Help button of the dialogs opens the page of this documentation that explains the recipe (every recipe has one; before, a name of a page of the documentation of Astrocook 1, which no browser could open); the section exists on the site from the next release. Help > Online Documentation and the button share the address of the documentation. For scripts and developers: RecipeSpec.menu, .menu_path, .title and .doc_url, registry.DOCS_URL; the url of a recipe is relative to the root of the documentation; four attributes of the window were renamed with the same meaning (auto_cont_action, find_abs_action, fit_cont_action, calibrate_action: now <recipe>_action). No number changes.

  • Optimize system and the Bayesian fit reviewed (phase 6-quater, PR 10-bis). The nested sampling of fit_bayesian works again (F139: with dynesty 3 it stopped with a TypeError after half a second, so almost always) and its values and errors are those of the posterior (F140: the medians and standard deviations were taken from the points of the sampler without their weights; on a CIV component the errors came out 1.7 in log N and 42 km/s in b instead of 0.005 and 0.14, as the MCMC gives); the samples stored for the corner plot have equal weights. The MCMC works with more than 16 free parameters (F141: its 32 walkers are now twice the free parameters when these are more; up to 16 the results are the same as before, and an error of the sampler is a failure of the recipe, not a crash). Refused before the recipe runs, with a message that names the parameter: a component that is not in the session (F142: optimize_system recorded a step that changed nothing, fit_bayesian failed with “cond is not defined on empty arrays”), and fewer than 10 live points per free parameter in nested sampling (with fewer dynesty failed or did not end). fit_bayesian: uuids is required (an empty list was a failure, “No components are selected”); a new parameter seed makes the sampling repeatable (left out, nothing changes); the warnings of dynesty go to the log. optimize_system: a new parameter max_nfev (default 1000, the value that was fixed); the descriptions of z_window_kms (also how far the redshifts move in its fits) and of max_components (the candidates tried, also those rejected) corrected. The results of optimize_system and of the MCMC do not change. The Refit Bayesian (MCMC) entry of the System Inspector no longer passes its own copies of the defaults.

  • The parameters of the manual fits of Absorbers reviewed (phase 6-quater, PR 10: Add component, update_component, update_components, delete_component, Detect doublet anchor redshift, fit_component, update_constraint, update_constraints_column, add_linked_system). No result of a valid call changes, but for the two cases below. Refused before the recipe runs, with a message that names the parameter: a component that is not in the session (F142: update, delete and fit recorded a step that changed nothing, update_constraint stored a constraint for no component); a series that is not in the atomic data (F143: update_component stored it and add_linked_system added a component without lines; Add component failed with “no valid pixels”), and a list of series given to Add component (CIV,SiIV: the message names add_linked_system) or a series given twice to add_linked_system; a call that changes nothing (update_component with the component alone, update_constraint without is_free and without an expression, delete_component without components); and, in update_constraint, an expression that cannot be evaluated (now an InvalidParameter, F117), one that names the component itself, an expression together with is_free=True (the expression was dropped without a word) and a target_uuid that the expression does not name (F146). The link of update_constraint without target_uuid takes as its target the first component its expression names, as the GUI gives it, and is stored frozen: the fits now put the target in the group of the linked component, as for the links made in the GUI (until 2.6.0 a link made by a script or an agent without target_uuid was fitted without its target). Detect doublet anchor redshift reads the flux normalized by the continuum (F145: it took the flux as normalized, so a spectrum in physical units gave a wrong redshift; a normalized one gives the same result), stops when the two transitions cover no redshift in common (it returned 0) or a flux has no continuum and is not normalized, and reads an axis in Å as well as in nm. Defaults: the redshift of Add component and of add_linked_system has none (it was 0, which never fell on the spectrum), nor have the transitions of Detect doublet anchor redshift, series_list of add_linked_system and is_free of update_constraints_column (the defaults the dialogs and the MCP schemas offered were not those of the methods, which had none: an agent that left them out got a TypeError, F144). A resolution of 0 in update_component(s) removes the resolution of the component, which follows the spectrum again (0 was refused, and the override could not be removed); update_components takes series like update_component (the string 'None' of the old logs still means “unchanged”). A required parameter starts empty in the dialogs (Add component: z). MCP server: these parameters are now required in the schemas of the tools.

  • Combining sessions with different units (phase 6-quater, PR 9): Stitch, Equalize and Stitch Arms and Co-add combine the sessions in the units of one of them, the reference (this session, the bluest arm, the first session listed), converting the others’ axis and flux before scaling them. Before, Equalize and Stitch Arms scaled an arm in another unit of the flux on its values and then converted it, so that an arm per nm came out 10 times too faint against one per Å (F132); Co-add co-added the values as they were (F133: 10 times too bright without scaling, right by chance with it); both looked for the overlap of a session with the axis in Å and one in nm in the values and found none, so the session was not scaled without a word, and Equalize and Stitch Arms applied the cuts in Å, keeping the whole arm, and could put the arms in the wrong order (F134). Sessions in one unit give the same results as before, to the bit. A flux in arbitrary units is combined with a physical one only when scaled to it (it takes its unit; Equalize and Stitch Arms refused it, Co-add mixed them), and a normalized flux is never combined with one that is not; an axis in velocity is refused against one in wavelength (convert it with Convert X axis). Equalize (Flux) had the same faults and compares the two sessions in the units of the current one (F138): the scaled flux keeps its unit, a flux in arbitrary units takes that of the reference. In scripts, Spectrum.coadd and Spectrum.equalize_to_reference compare in the units of the reference too, and the latter refuses an axis in velocity against one in wavelength (a ValueError).

  • The recipes that read other sessions (phase 6-quater, PR 9): one rule for all (Import Systems from Session, Trim to common velocity coverage (trim_common), Stitch, Equalize and Stitch Arms, Co-add, Equalize, Resample, Detect doublet anchor redshift (detect_anchor)). The other sessions are named by the names of the Session List (in the MCP server, their session_id), separated by commas where several; the name of the session the recipe runs on is that session. In a Python script they also take the sessions themselves (session.edit.coadd([session, other])), and the log records their names: in a script without the GUI, Co-add, Equalize and Stitch Arms, Import Systems from Session and trim_common crashed with an AttributeError (F135). A name that is not that of an open session stops the recipe and names it: Co-add skipped it without a word, Stitch with a warning, trim_common said “no range in common” (F136). Stitch takes the names as a comma-separated string too (a list, as before, still works); trim_common’s others_names is now other_sessions, as in the other recipes (the old name still accepted).

  • The parameters of the recipes of Edit on several spectra reviewed (phase 6-quater, PR 9). Co-add: the list of sessions must include this session (the result is a new state of it: without it, it held the others only, F137); equalize_order is None for no scaling and 0 to 5 for a polynomial (F123: it was -1, which in Equalize means a spline; -1 is still read as None, so the session logs replay); xstart must be below xend (it gave a spectrum without pixels), and xunit must be a velocity or a wavelength. Split has no default expression (it was (λ > 400) & (λ < 500)); Import Systems from Session requires the session (its default was the string 'None'). Refused before the recipe runs, with a message that says why: Equalize and Stitch Arms with cuts not increasing or an arm without pixels between its cuts, factors not positive (0 zeroed the flux) or a range whose start is not below its end (they failed with “Split expression resulted in an empty spectrum”); Delete Elements with nothing, a column of every spectrum (λ, F, dF, …) or one the spectrum does not have (a warning, and a step recorded as done); Extract Preset Region with an unknown region (skipped with a warning when others were valid); trim_common with a transition not in the atomic data (“no range in common”, or ignored) or not one per session. MCP server: the tools that read several sessions say x-astrocook-kind: sessions in their schema, edit_stitch takes a string, and edit_split requires expression, edit_import_systems source_session. For developers: equalize_and_stitch split into helpers (its complexity from 23 to at most 10).

  • The unit of the flux (phase 6-quater, PR 8-bis): a spectrum gets a physical unit of the flux only when the file says it, otherwise its flux is in arbitrary units, the new unit arb_flux of Astrocook (astrocook.core.units.ARBITRARY_FLUX; astropy.units.Unit('arb_flux') once Astrocook is imported). The values never change, only the unit. Before, most loaders gave the flux erg/(Angstrom s cm2) or no unit whatever the file said. Now: the FITS files of Astrocook, X-Shooter (TUNIT of FLUX, unless FLUXCAL = 'UNCALIBRATED') and the generic FITS loader (TUNIT of the flux) read the unit of the file; ESPRESSO S2D reads BUNIT (per Å, as the loader divides by the width of the pixel); PypeIt, the CSV files without units, the telluric ASCII files, the files with RESVEL, the archives of Astrocook 1 (which write no units) and the archives whose flux has no unit open in arbitrary units (the transmission of a PypeIt telluric model stays dimensionless). An archive with a unit keeps it. With an arbitrary flux the plot says “arbitrary units”, the iso-magnitude grid is not drawn (it was drawn for spectra that were not calibrated; its check box says why), Convert Y axis refuses to convert it, and Flux Calibrate reads it as erg cm⁻² s⁻¹ Å⁻¹ (it failed). Declaring the unit: Set Properties has a new field, yunit (default _current_), which gives the flux, its error, the continuum and the model a unit without changing the values (e.g. 1e-17 erg/(Angstrom s cm^2), or arb_flux); Convert Y axis converts. In the archives arb_flux is written in the TUNIT of the columns (it is not a unit of the FITS standard: Astrocook 2.6.0 reads it with a warning; other FITS readers show the string). MCP server: y_unit is arb_flux for an arbitrary flux; the tool edit_set_properties takes yunit.

  • Convert Y axis converts the continuum and the model also when they have no unit, in archives saved by earlier versions (F130): they were left as they were, so the flux divided by the continuum changed by the factor of the conversion (e.g. 10 from Å to nm). When such an archive is opened, the continuum and the model without a unit take the unit of the flux.

  • Flux Calibrate keeps the unit of a flux that has one (F131): the result was always labelled erg cm⁻² s⁻¹ Å⁻¹, with the values in the unit of the flux, so a spectrum in erg cm⁻² s⁻¹ nm⁻¹ came out labelled 10 times brighter than the magnitudes asked for (2.5 mag). The values do not change; a flux in arbitrary units or without a unit takes erg cm⁻² s⁻¹ Å⁻¹, as before.

  • The CSV files of Export to ASCII (phase 6-quater, PR 8-bis, F129) are written in ECSV, the CSV format of astropy: comment lines with the unit of each column and the emission redshift, then the names and the values separated by commas (pandas.read_csv(path, comment='#') reads them). The columns of the spectrum have the names of the GUI in ASCII, lam, lammin, lammax, F, dF (they were x, xmin, xmax, y, dy); the file of the systems does not change. Opened again, the file gives back all its columns, their units and z_em: before, the loader took the first three columns as wavelength in nm and flux in erg/(Angstrom s cm2), so a flux converted to another unit or an axis in km/s came back with the wrong unit, the continuum was lost, and the file of the whole spectrum (x,xmin,xmax,y,dy,...) came back with xmin as the flux. The files of earlier versions are read by the names of their columns (x, y, dy, …), with the flux in arbitrary units; other CSV files as before, by position. Import from ASCII understands the names of the GUI (a column F replaced an auxiliary column F instead of the flux), skips lam, lammin and lammax as it skips x, keeps the units of the file, and refuses a flux in a unit different from that of the session.

  • One set of names of the columns (phase 6-quater, PR 8, F120): wherever a column is named (the expressions and the fields of the recipes, scripts, the MCP server) the names are those of the table of the GUI, λ, λmin, λmax, F, dF, and the other columns by their own name (cont, model, …); λ can be written lam (lammin, lammax). The names in the data, x, xmin, xmax, y, dy, are still accepted everywhere, so the session logs, the saved expressions and the scripts written with them work as before; the archives keep them (the CSV files of Export to ASCII kept them until PR 8-bis). Calculate Running StdDev now finds F (the button of its dialog: it failed) and its default input is F (it was y, the same column); it no longer writes a column named F, dF or λ, which no expression could read. MCP server: spectrum_read reads F, dF, cont and model by default and gives the axis as λ (or under the name asked for it: x, lam; it was always x); session_describe lists the columns by these names.

  • The parameters of the recipes of Edit on columns and expressions reviewed (phase 6-quater, PR 8). No result of a valid call changes. Apply Expression has no default target and expression any more (they were F and F / dF, which replaced the flux with its S/N; in the MCP tool both are now required); its target must be a name an expression can use (letters, digits and _: '' and 'a b' made columns that no expression could read). Apply Expression, Mask by Expression and Smooth Column refuse the axis (λ, λmin, λmax) as their target (they replaced, masked or smoothed the wavelengths, F127): Convert X axis changes it. Refused before the recipe runs, with a message that says why: a column to mask or smooth that does not exist (the message lists the columns), an empty name of a session in Set Properties (it was ignored), a unit of Convert X axis that is neither a wavelength nor a velocity, a unit of Convert Y axis that the flux cannot take (e.g. Jy: a flux per unit wavelength only). A function the expressions do not have (median, mean, std) is named as such instead of “‘VariableNode’ object is not callable” (F128). The descriptions say where the zero of the velocity axis is (the Lyman-α emission at z_ref).

  • The parameters of the recipes of File and Flux reviewed (phase 6-quater, PR 7). No result of a valid call changes. Export to ASCII: the folder is folder (it was path, still accepted, in scripts and in the MCP tool file_export_ascii), and the items not found in the session (e.g. cont without a continuum, or a misspelt systems) are named in a warning instead of being skipped silently. Equalize and Resample require the session they read (reference_session, target_session; their default was the string 'None', which still fails as before saying that no session is selected; in the MCP tools the parameter is now required). Refused before the recipe runs, where they gave an empty or hidden result without a word: Rebin with xstart not below xend (a spectrum without pixels), Equalize with order below -1 (a spline, as -1), Calculate Running StdDev writing to an empty name or to a column of every spectrum (x, xmin, xmax, y, dy: the result went to a hidden column), Flux Calibrate with magnitudes not written as Filter=Magnitude pairs or with an unknown filter (it failed when it ran; the description lists the filters). Rebin warns that norm is ignored for any true value ('true', 1), not only 'True'. The methods text of Calculate Running StdDev gives the window used (an even window is increased by 1), not the one passed.

  • The classes lost the V2 suffix of their names (phase 6-quater): SpectrumV2 is now Spectrum, SessionV2 is Session, DataColumnV2 is DataColumn, RecipeAbsorbersV2 is RecipeAbsorbers, and so on for the 21 classes of the package. For scripts: the old names still import and give the same class, with a DeprecationWarning; they will not be removed before 3.0. The archives (.acs2) and the session logs are not affected: they hold no class names. The settings saved by the GUI are kept.

[2.6.0] - 2026-11-10#

Phase 6-ter of the consolidation: the full MCP server. Astrocook can be driven by an AI agent through 65 tools: the 48 recipes (each one a tool, generated from the registry), the sessions with undo and redo, the inspection of a session, the notes and gaps of the agent, the log as the text of a methods section, the cancellation of a long recipe, a GUI that follows a session of the server and a headless Docker image. Outputs come from RecipeResult only, and nothing the agent does is lost. A minor version: the interface of the server grows, the results of the recipes do not change but in the two cases below.

Numerical results. Unchanged for the benchmark of synthetic spectra (documentation page Accuracy, as for 2.2.0) and for the fits and the identification in general, with two changes decided on purpose (PR 7-quater). (1) Check associated metals (metals_auto) refitted the session it started from and lost the ions already found, and kept a trial ion if its fit gave logN >= 12 and 2 <= b <= 50 km/s (aic_penalty was accepted and not used). It now keeps the ions found, skips the ions whose lines fall outside the spectrum (with a warning) and keeps a trial ion only if its fit does not end at a bound (b or logN) and its AIC change is below -aic_penalty (F111, F121); on a real spectrum (J0103-1305 raw, 215 thousand pixels) the recipe went from 192 ions kept, 67 of them at b = 50 km/s, to 82 and none at the bound, and from 26.7 to 6.4 minutes for the trials. The benchmark of synthetic spectra does not run metals_auto: a targeted test measures it (the SiIV of the mock of the trials is found). (2) A fit of components with no valid pixel around them no longer fits the whole spectrum: the components are not fitted and keep their first values (F111). Published on GitHub with the macOS app; not on PyPI yet (install with pip from GitHub).

Changed#

  • Using Astrocook from an AI Agent rewritten for the full MCP server (phase 6-ter, closing): installation and Docker, the tools by group, a longer example (a blend fitted with undo and constraints), what a request should say, the review in the GUI and the limits (the automatic recipes, no measure of the fit, z_em and R not estimated, the cost in context of the 65 tools). The server is no longer called a pilot.

  • MCP server for agents (phase 6-ter): every recipe is a tool, named <menu>_<recipe> (e.g. flux_rebin, absorbers_fit_component), made from the description of the recipe that the GUI dialogs use: the same parameters, defaults, bounds and texts, the values checked as in the GUI; a recipe added to Astrocook becomes a tool with no change of the server. The five tools of the pilot keep their names. Every tool returns what the recipe changed, listed (the components removed with the reason, the components changed, the columns, the properties), with the summaries of the pilot where they apply (continuum, identification, fit). A recipe that opens new sessions in the GUI does so in the server too, each with its own session_id, and leaves the session it ran on unchanged: Identify Absorption Lines now opens a new session (in the pilot it changed the same one). A parameter that names another session (e.g. the reference of Equalize) takes its session_id. The messages name the tools that provide what is missing (edit_set_properties, continuum_estimate_auto).

  • MCP server: tools for the sessions, session_list, session_describe, session_history, session_undo, session_redo, session_duplicate and session_close (phase 6-ter). Every state of a session is kept, as in the GUI: what a recipe removed is had back with session_undo, and the result of such a recipe says so. session_close does not close a session with changes not saved unless asked to discard them.

  • MCP server: tools to look into a session without changing it (phase 6-ter): components_list (the components with their errors, flags, fit groups and constraints, filtered by series, redshift and flags), spectrum_read (the columns of the spectrum in a range, as numbers) and spectrum_plot (a plot of a range, as an image). What they compute is in the package, for scripts too: SystemListV2.fit_groups (the groups of components that Refit All fits together, now also used by Refit All itself, with the same results), SpectrumV2.columns_in_range (the columns in a range, averaged in blocks of pixels if asked) and the new module astrocook.plotting (plot_spectrum: a plot of a session without the GUI, with the colours of the GUI; the palettes of the plots moved there from gui/plot_style.py). See Using Astrocook from Python, “Looking at a Session”.

  • MCP server: long recipes (phase 6-ter, F113). After 20 s without a line in the log a recipe sends a heartbeat as a progress notification (“Still running : N s; last: ”), so that a client does not give up; the read-only tools, session_save and session_note answer while a recipe runs, on the state before it (session_list and session_describe say what is running; session_save warns). The [mcp] extra now needs anyio>=4.11.

  • Cancellation of a recipe (phase 6-ter, F111, F113): one signal for the GUI’s Stop and the MCP server. The new tool session_cancel stops the recipe running on a session (the recipes check the signal; RecipeCancelled in a script) and the session keeps its state before it. metals_auto checks it at each trial ion, writes a progress line per trial and reports the AIC change of each ion tried (details.tried).

  • The result of every recipe has a details field with what the recipe reports besides the changes (the optimization trace of Optimize, the candidates Identify lines scored and dropped, with their score, dropped_candidates), no recipe named in the server (F118, F119). update_constraint checks every new link, also with is_free left out, and its example is p['<uuid>'].z (F117). spectrum_read also accepts the names of the columns of the GUI (λ, F, dF, …) (F120). compare_sessions lists a parameter as changed only beyond a relative tolerance of 1e-8, so a refit that changes nothing no longer adds “changed” components to the methods text.

  • Export to ASCII no longer replaces files that exist unless asked (F106): in a script, session.file.export_ascii(..., overwrite=True); without it, the export stops, writes nothing and names the files. The GUI asks, as before, and replaces them if you say so. A script that exports twice to the same files must add overwrite=True. The recipe declares its prefix (the beginning of the file names), so that it is also a tool of the MCP server (file_export_ascii).

  • MCP server: progress notifications (phase 6-ter). The recipes that report their progress in the log (>> PROGRESS: n: the automatic pipelines, Refit All, the Bayesian fit) send it to the client as MCP progress notifications, with the last line of the log as the message, as the GUI shows it under its bar; every recipe sends one notification when it starts and one when it ends, with its duration. A client that does not ask for progress receives nothing. For scripts and developers, the format of the progress lines is read in one place, astrocook.recipes.progress (parse_progress, and watch_progress(callback), which calls a function for each progress line a recipe logs); the GUI uses it, with no change in what it shows.

  • The agent’s decisions in the session log (phase 6-ter): every recipe tool of the MCP server takes reason (why the agent runs it, with these values), stored with the step in the log, and the new tool session_note writes a note at the current state of a session (what the agent did or decided outside the tools). A note is not a step: no new state, skipped by the replay, undone with its state. Both are saved in the .acs2 archive and shown in the session log of the GUI as comments (# reason: ..., # note: ...); Run All keeps them in the log it rebuilds. The archives saved before open and replay as before; Astrocook 2.5.0 and earlier open the new archives and replay them, but ignore the reasons and notes (and lose them if they save the session again). For scripts: log.add_entry(..., reason=...), log.add_note(text), log.timeline() of HistoryLogV2.

  • The gaps of the collection of recipes (phase 6-ter): what an analysis needed and no recipe provided. The MCP server records them, in the log of the session and in a file on your computer (~/Library/Application Support/Astrocook/gaps.jsonl on macOS, $XDG_DATA_HOME/astrocook/gaps.jsonl or ~/.local/share/astrocook/gaps.jsonl on Linux, %APPDATA%\Astrocook\gaps.jsonl on Windows; one JSON line each with date, version, kind, text and the name of the session, never sent anywhere; ASTROCOOK_GAPS_FILE moves it, off turns the record off). The agent declares a gap with session_note(..., kind="gap"); the server records by itself a prerequisite that no recipe estimates (z_em, the resolution), a tool that failed with an unexpected error on a valid request (the error type, not its message) and a recipe whose result the agent undid (session_undo takes a reason). The new command astrocook-gaps and the tool gaps_summary summarize them, grouped, to plan the next recipes. For scripts: astrocook.gaps (record_gap, read_gaps, summarize); the notes of a log have the kinds gap and gap_seen, shown as # gap: in the Log Scripter.

  • The session log as the text of a methods section (phase 6-ter): File > Export Log as Text… shows the log of the active session as English text, ready to paste in a paper and to edit, with Copy and Save…: a first paragraph on the spectrum and the version of Astrocook, one paragraph per recipe (the reason given for it, e.g. by an AI agent; what it did, with its parameters and the works it relies on; what it changed: the components added and removed by ion with their range of redshift, the median and largest changes of a refit, the columns, the parameters left at a bound of the fit; the notes written there), the Voigt fit and the sources of the atomic data of the transitions fitted, and the references. The recipes undone are left out; the menu of each recipe follows it in parentheses, unless Name the menus of the recipes is unchecked. For an archive just opened, the text gives the recipes and their parameters, not what each changed. The MCP server offers it as the tool session_methods; scripts as astrocook.methods_text.methods_text(history). For developers: the keys methods (a template of the parameters, or a function of them) and references of a recipe in the registry; every recipe has them.

  • The GUI follows a session of the MCP server (phase 6-ter): the new tool gui_open opens a session in the Astrocook GUI (the application with open -a Astrocook on macOS, else the astrocook command) and keeps it up to date: the server saves it to an archive of its own after every change (a recipe, the steps provided first, undo and redo, a note), and the GUI reloads it, keeping the view (the range and zoom of the plot, the System Inspector and its selected row). A banner says that the session is followed and read only in the GUI: the recipes that change it, the continuum editor, Undo and Redo, the scripts and renaming are refused, with the offer of an editable copy (Make Editable Copy, with the log of the session); saving, exporting and the recipes that open a new session are allowed. When the agent closes the session or the server stops, the banner says it is no longer followed. Without a display (e.g. a Docker image) the tool says that the GUI is not available. An archive is followed when a small file next to it says so (<archive>.follow.json); the archive is replaced only when complete, so the GUI never reads it half written. For scripts and developers: astrocook.follow (write_archive, write_marker, read_marker, remove, gui_unavailable_reason, gui_command, launch_gui), so that any program can be followed by the GUI.

  • A headless Docker image of the MCP server (phase 6-ter): the Dockerfile of the repository builds an image with the server and no GUI (no PySide6 and no Qt libraries), for those who would rather not install Python and the packages: docker build -t astrocook-mcp ., then docker run -i --rm -v <data>:/data astrocook-mcp, which a client (Claude Code, the Claude desktop app) starts by itself; the files of the user are the folder mounted in /data. The tools are the same as in an installation; gui_open says that the GUI is not available. The image is not published. See Using Astrocook from an AI Agent, section 2.1. [2.5.0] - 2026-11-05#

Phase 6-bis of the consolidation: the recipe API, for scripts, the GUI and the AI agents. Every recipe is described once (its parameters, their types, limits and values allowed, what it needs from the session and what it provides), and the GUI, scripts and the MCP server read that description. In a script the parameters can be given typed or as strings, and values without a physical meaning are refused. A recipe that cannot do what was asked raises an exception that names it, its step and the reason, instead of returning 0: a script that checked for 0 must catch RecipeError instead. run(session, "absorbers.doublets_auto") gives the whole result (what changed, the warnings, the components removed and why). A recipe that needs a continuum and finds none estimates it first (scripts), asks (GUI) or says so (agents). The descriptions of all the recipes are reviewed, and the dialogs offer lists for the parameters with a few values. The session logs of earlier versions replay with the same results.

Numerical results. Unchanged for the benchmark of synthetic spectra (documentation page Accuracy, as for 2.2.0), and in general, with two changes decided on purpose. (1) Identify lines, the automatic pipelines and Check associated metals, on a spectrum without a continuum (flux not normalized), identified the absorbers on the raw flux; the continuum is now estimated first (F103), so their results change for such spectra (not for normalized ones). (2) Auto-fit Ly-alpha forest no longer refits the components outside the forest in its cleanup (F102): metal lines fitted before on the red side keep their values. A minor version, as 2.4.0: the interface of the recipes for scripts changes, the results do not. Published on GitHub with the macOS app; not on PyPI yet (install with pip from GitHub).

  • The parameters of all the recipes are typed: a script can give them as numbers and True/False (session.flux.smooth(sigma_kms=50)) or as strings, as the dialogs and the session log do; they are converted once, before the recipe runs, and a value that cannot be read stops the recipe with an error that names the parameter (e.g. sigma_kms: ‘fifty’ is not a number).   • What a recipe needs from the session (the emission redshift, the resolution, a continuum) is declared with the recipe, with the recipes that provide it, and checked before it runs (astrocook.recipes.prerequisites). A script goes on as before: a missing continuum is estimated first with Auto-estimate Continuum, now with a warning (it was an information), and is a step of its own in the session log, before the recipe; with policy("raise") or run(..., on_missing="raise") the recipe stops instead with an error that says what is missing and which recipe provides it. [2.4.0] - 2026-11-03#

Phase 6 of the consolidation: error handling. Astrocook now says when something goes wrong, instead of going on with a result that looked valid: a recipe that cannot do what was asked stops with its reason (in the status bar, a dialog and the log), a bug in the GUI is shown in a dialog with its details, and the messages of the log follow one rule. The results of fitting, identification and the automatic pipelines do not change when nothing goes wrong: the results on the benchmark of synthetic spectra are those of 2.2.0 and 2.3.0 (documentation page Accuracy). What changes is the behaviour on failures, listed under “Fixed”: some operations that returned a result (often the input unchanged) after an error now fail with the reason, for example Auto-fit Ly-alpha Forest without the emission redshift, or a V1 archive whose systems cannot be read. One fix prevents a data loss: a failed save no longer replaces the archive with a partial one (F94). Published on GitHub with the macOS app; not on PyPI yet (install with pip from GitHub).

Added#

  • GUI: an error that nothing handled (a bug) is shown in a dialog, with the message and, under Details, the traceback to attach to a report; it was written only to the terminal, and the action stopped without a sign. Astrocook goes on after it.

Changed#

  • Each module of Astrocook logs with its own logger, named after the module (astrocook.recipes.absorbers, astrocook.fitting.voigt_fitter, …), instead of the root logger: a script can choose the level of Astrocook’s messages, or of a part of it, alone (logging.getLogger("astrocook").setLevel(logging.INFO); see Seeing Astrocook’s Messages in the scripting tutorial). The messages themselves and what the GUI shows do not change.

  • The messages of the core, the fit, the loaders, the recipes and the GUI follow one rule (phase 6): English sentences without the name of the function in front, values with their units, and the level by what the user needs: INFO for what an operation did, WARNING when the result needs a check or something was done instead of what was asked, ERROR when there is no result, DEBUG for the internal steps (e.g. the candidates tried by Optimize System, which were WARNING or INFO, are now DEBUG; its accepted components stay INFO). An error is logged once, where it is caught, with its context (e.g. Could not read bad.fits as astrocook_fits: …, or the expression that could not be evaluated), instead of two or three times along the way.

Fixed#

  • Saving a session no longer risks losing the file it replaces (F94). The .acs2 archive was written directly over the existing file, which was emptied first: if the save failed while writing (e.g. a full disk, or an error in the original data of the session), the previous archive was left partial or empty. The archive is now written to a temporary file in the same folder and replaces the old one only when complete; a failed save leaves the old file as it was, and the error is shown as before. An error in the original data now stops the save at once: it was logged and the save went on, to fail later with a confusing “No such file or directory”.

  • Failures that went unnoticed now stop the operation with a message (phase 6). Before, Astrocook went on with a result that looked valid and wrote the problem only in the log, or nowhere:

    • a link between parameters that could not be evaluated (a syntax error, or a component that no longer exists) kept the parameter at its old value in every fit, silently: such a link is now refused when it is set (in the System Inspector, or with the update_constraint recipe), and a session saved with one opens with an error that names the parameter, kept frozen at its value;

    • the manual continuum with two knots at the same wavelength, a single knot or none was not saved, with an error in the log only: the editor now says why in a dialog; Fit continuum with fewer than two unabsorbed pixels gave back the spectrum unchanged, and now fails with the reason;

    • a V1 archive (.acs) whose system list cannot be read opened without its systems (which a save in .acs2 then lost): it now fails to open, with the reason, as a V2 archive does;

    • the smoothing of a continuum or of the flux, the merging of absorbed regions and the search of doublet candidates gave back their input unchanged (or no candidates) when the x axis could not be converted to km/s: the recipe now fails with the reason;

    • an unknown region (region_limit), or one that cannot be computed because z_em is not set, made the automatic pipelines (Auto-detect Doublets, Auto-fit Ly-alpha Forest) and Refit All Systems work on the whole spectrum, with a warning: they now fail with the reason;

    • deleting components, importing systems from a session that is not open, trimming sessions without a range in common and stitching without sessions gave back the session unchanged, which looked like a success: they now fail with the reason;

    • Equalize and Stitch replaced manual factors or equalize ranges that could not be read (or not one per session) with auto: it now fails with the reason;

    • in Refit All Systems, a group whose fit fails keeps its values, as before, but the groups are now counted in one warning with their redshifts instead of one line each; in Check Associated Metals, the trial fits that fail are counted in a warning (they were reported only at the debug level);

    • a fit on a spectrum without a resolution (fitted with profiles that are not convolved, so the b values include the instrumental broadening) now gives a warning in scripts and to agents too (it was only at the debug level; the GUI asks for the resolution first, as before); when a fit recipe estimates the missing continuum first and that fails, the recipe stops with the reason (it failed with ‘int’ object has no attribute ‘systs’); Refit All Systems now says when it estimates the continuum;

    • saving a session says when the samples of a Bayesian fit are not saved (the archive cannot hold them yet; astropy skipped them with a warning of its own), and no longer prints the warnings of astropy that did not matter (the keywords of the FITS structure in the metadata of a session opened from a V1 archive, the long keywords of an identification);

    • a failed Export to ASCII now says so in a dialog (it showed nothing); an entry of the session log that cannot be written stops the update of the session with an error, instead of being dropped while the result was applied (the log and the replay then differed from the session);

    • when the removal of the narrow lines at the end of the forest pipelines fails, the result is kept, as before, and the warning now says how many narrow lines it still contains; when the refit of imported systems fails, the import is kept with a warning that says so.

  • A .csv file of numbers only (wavelength, flux, error, without a line of names on top) did not open (F100): the first line was taken as the names of the columns, which had to be col1, col2, col3. The first three columns are now read by position, with or without a header of any names; Getting Started says how a CSV file is read.

  • A .csv file of fewer than 10 lines did not open (F97): the detection of the format stopped at the end of the file and sent it to the loader of FITS files, which failed with “No SIMPLE card found”.

  • A script that ran a recipe before configuring logging could no longer configure it (F96): the first message of the recipe set up Python’s logging with its defaults, so a later logging.basicConfig(level=logging.INFO) was ignored. A script that configures nothing still sees the warnings and errors, now without the WARNING:root: prefix.

[2.0.2] - 2026-10-16#

Corrective release. Some numerical results change: see “Changed behaviour” below.

Fixed#

  • Data loss: Bayesian fit (MCMC) with 200 steps or fewer overwrote the component parameters with NaN; the burn-in now adapts to the number of steps.

  • Data loss: the .acs2 archive did not keep the session log; it is now saved and restored (also in the GUI).

  • Voigt fits of broad lines (b > 50 km/s) were biased (e.g. b = 80 fitted as ~50, logN 0.1 dex low): the soft penalty is removed (see below).

  • Rebinned and co-added errors did not decrease with the number of pixels per bin (#490).

  • Rebin clipping could empty bins and removed the cores of narrow absorption lines; it now clips spikes only (upward, against a running median) and never empties a bin.

  • The Voigt model was zero on pixels whose resolution column held non-round or NaN values (e.g. co-added spectra).

  • The automatic pipelines (doublets_auto, lya_auto, …) gave different results at every run; they are now reproducible.

  • Components could not be deleted from a spectrum without a continuum.

  • group_depth was ignored in the fits (“Fit component”, Bayesian fit).

  • Rebin with a non-numeric parameter raised an error instead of aborting cleanly.

  • The identification viewer failed on sessions reloaded from .acs2.

  • NaN uncertainties (ill-conditioned fits) are now reported in the log with the components involved.

  • ASCII export (#476, #481); warning when saving a session with a V2 log to the V1 .acs format.

Added#

  • Edit > Import Systems from ASCII: read absorption components from a CSV or whitespace-separated table (columns series, z, optionally logN, b, …) (#480).

  • Stitching overlapping regions switches the plot to scatter style (#442).

  • max_b parameter of the automatic pipelines (default 50 km/s) and of Refit All (default 300 km/s).

Changed behaviour#

  • Uncertainties: the errors of the fitted parameters are scaled by sqrt(reduced chi2), as in Astrocook v1; the reduced chi2 is computed on the pixels that constrain the fit and, after the automatic pipelines, on the final model. Errors become larger where the model does not describe the data well (e.g. unresolved blends).

  • Broad lines: the automatic pipelines bound b to 50 km/s (as the former penalty did, but without biasing the fits); manual fits use only the physical limit (300 km/s). Components that end at 50 km/s may be broader and can be refitted by hand.

  • Continuum smoothing: the width is now given as a FWHM (smooth_fwhm, default 800 km/s, which reproduces the v1 continuum). The former smooth_std (a standard deviation, default 500 km/s) is still accepted. The default continuum is smoothed less than in 2.0.1, so continua and the results of the automatic pipelines change slightly.
